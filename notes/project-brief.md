# hts-tick-viewer — 면접 준비용 프로젝트 브리핑

> 이 문서는 **면접 문답을 시뮬레이션할 다른 세션에 넘기기 위한 자료**다.
> 프로젝트가 무엇이고, 만든 사람이 무엇을 직접 겪었는지를 정리했다.
> **의도적으로 "모범 답안"은 적지 않았다.** 답은 본인 입에서 나와야 한다.

---

## 1. 만든 사람 배경

- 실무 경력은 **Java/Spring 과 Python**.
- **C++ 경험은 사실상 없음.** 학부 1학년 C 수업이 전부.
- 이 프로젝트가 첫 C++ / Win32 / MFC 경험이다.
- 따라서 질문은 "C++ 문법 퀴즈"보다 **"이 프로젝트에서 무엇을 왜 그렇게 했는가"** 로 가는 편이 유효하다.
- Java와의 대조(GC vs 수동 해제, 참조 vs 포인터, 스레드/UI 모델)를 물으면 답할 준비가 되어 있다.

## 2. 프로젝트 개요

증권사 HTS의 **'시간대별 체결'** 화면을 아주 작게 흉내 낸 Windows 데스크톱 프로그램.

TCP 소켓으로 체결 데이터를 실시간 수신해서 MFC 창의 목록(List Control)에 한 줄씩 쌓는다.
데이터를 흘려보내는 **더미 서버(Python)** 도 같은 저장소에 둔다.

목적은 결과물 자체보다 **C++, Win32 소켓, MFC를 손으로 익히는 것**이었다.

## 4. 프로토콜

접속 대상은 `127.0.0.1:9000`.

한 건의 형식:

```
[ 길이 4바이트 ][ 본문 ]
```

- **길이**: 본문의 바이트 수. **big-endian(네트워크 바이트 순서) 부호 없는 4바이트 정수**
  - 서버: `struct.pack(">I", n)`
  - 클라이언트: `ntohl()` 로 되돌림
- **본문**: ASCII 문자열 `HHMMSS|종목코드|가격|수량`

실제 바이트 예시 (본문 25바이트):

```
00 00 00 19  31 35 32 32 33 33 7C 41 30 31 36 39 ...
└─ 길이 25 ─┘ └──── "152233|A0169000|1099.70|3" ────┘
```

수량이 두 자리면 본문이 26바이트가 되어 길이 프리픽스도 `00 00 00 1A` 로 바뀐다.

### 서버의 세 가지 전송 모드

클라이언트 파서를 일부러 괴롭히기 위해 만든 것이다.

| 명령 | 동작 | 무엇을 시험하나 |
| --- | --- | --- |
| `py dummy_server.py` | 0.5초마다 한 건 | 기본 동작 |
| `py dummy_server.py --burst` | 3건을 **한 번의 `sendall`** 로 붙여서 전송 | 여러 건이 뭉쳐 도착하는 경우 |
| `py dummy_server.py --split` | 한 건을 **앞 2바이트 / 나머지** 로 쪼개 0.2초 간격 전송 | 길이 프리픽스조차 덜 온 경우 |

`--split` 의 절단 위치가 하필 **2바이트**인 것이 핵심이다. 절반에서 자르면 길이 4바이트는
온전히 도착해서 더 쉬운 경우만 시험하게 된다. (이 값은 튜터 세션의 제안을 받아들인 것이다. 9절 참고.)

## 5. 최종 아키텍처

```
[Python 서버]   체결 생성 → 길이 프리픽스 부착 → TCP 전송
                                  |
[워커 스레드]   recv → 누적 버퍼에 쌓기 → 경계 파싱 → new std::string
                                  |  PostMessage(WM_TICK_RECEIVED)
[UI 스레드]     메시지 수신 → delete → CString 변환 → CListCtrl 삽입
```

주요 구성 요소 (`client/hts-viewer/hts-viewerDlg.cpp`):

- `ConnectAndReceive()` — 워커 스레드에서 도는 소켓 수신 + 파싱 루프
- `ReceiveThreadProc(LPVOID)` — `AfxBeginThread` 에 넘기는 **static** 함수. `this` 를 인자로 받아 캐스팅
- `OnTickReceived(WPARAM, LPARAM)` — UI 스레드 측 메시지 핸들러
- `AddTickFromBytes(const char*, int)` — 바이트 열을 `|` 로 쪼개고 `CString` 으로 변환
- `AddTick(const CString&, ...)` — 실제로 목록에 행을 추가. 최신이 맨 위(`InsertItem(0, ...)`)
- `OnDestroy()` — `closesocket()` 으로 블로킹 중인 `recv` 를 깨워 스레드를 종료시킴
- `MAX_ROWS = 500` — 목록이 무한히 쌓이지 않도록 오래된 행을 삭제

## 6. 진행 순서

`README.md` 의 4단계를 순서대로 밟았고, 각 단계가 커밋 단위로 남아 있다 (총 22개 커밋).

**0단계 — C++ 기초를 콘솔로**
포인터와 역참조, `new`/`delete`, 스택 vs 힙 주소 비교, 클래스와 소멸자, 스코프별 소멸 시점,
복사 생성자와 값 의미론, 참조(`&`)와 `const` 멤버 함수, 값/`const&`/`&` 전달 비교.

**1단계 — 더미 서버 + 콘솔 TCP 클라이언트**
Python 서버를 접속 수신부터 한 걸음씩 작성. 이어서 Winsock 콘솔 클라이언트를 만들고
길이 프리픽스 파서를 붙였다.

**2단계 — MFC 창과 List Control**
대화 상자 기반 MFC 프로젝트, `CListCtrl` 을 Report 뷰로 배치, 열 4개 구성, 가짜 데이터 표시.

**3단계 — 통합**
소켓 수신을 워커 스레드로 분리하고, `PostMessage` 로 UI 스레드에 데이터를 넘겨 목록에 실시간 표시.

## 7. 직접 겪은 문제들 — 면접 소재

**모두 실제로 화면에서 확인한 것들이다.** 이 목록이 이 프로젝트의 핵심 가치다.

1. **`recv` 한 번 ≠ 메시지 한 건.**
   기본 모드에서는 29바이트씩 1:1로 떨어져서 "한 번에 한 건씩 오는구나" 하고 넘어갈 뻔했다.
   `--burst` 로 바꾸자 `recv` 한 번에 **87~89바이트(3건)** 가 왔고, `--split` 에서는 **2바이트**만 왔다.
   클라이언트 코드는 한 줄도 안 고쳤는데 결과가 달라졌다.

2. **구분자 없이 보내면 경계를 알 수 없다.**
   길이 프리픽스를 붙이기 전 출력이 이랬다.
   `172758|A0169000|1101.25|9172758|A0169000|1100.04|5...`
   첫 건의 수량이 `9` 인지 `9172758` 인지 확정할 방법이 없었다.

3. **화면은 거짓말을 한다.**
   `[수신 바이트: 29]` 인데 화면에는 25글자만 보였다. 길이 프리픽스 `\x00\x00\x00\x19` 가
   콘솔에 그릴 모양이 없는 제어문자라 안 보였던 것. 본문이 26바이트인 건은 길이가 `\x1A` 라
   `␦` 로 화면에 새어 나왔다. → **바이트 수를 같이 찍어두지 않았으면 몰랐을 일.**

4. **`if` 로 한 번만 꺼내면 밀린다.**
   `--burst` 에서 한 번에 3건이 들어오는데 1건만 꺼내니 매 라운드 약 58바이트씩 누적됐고,
   화면에 뜨는 시각이 실제 시간보다 점점 뒤처졌다. 약 35초면 4096바이트 버퍼가 찬다.
   `while` 로 바꾸자 누적이 0으로 돌아왔다.

5. **길이를 검증하지 않으면 위험하다.**
   `bodyLen` 은 외부에서 들어온 값이다. `4 + bodyLen` 이 `unsigned int` 범위를 넘으면
   작은 수로 되돌아가 검사를 통과하고, 버퍼 바깥을 읽게 된다.

6. **UI 스레드에서 `recv` 하면 창이 안 뜬다.**
   `OnInitDialog()` 에서 20건을 받게 했더니 **창이 10초 동안 나타나지 않다가 20줄이 채워진 채로** 떴다.

7. **워커 스레드에서 UI 컨트롤을 직접 만지면 안 된다.**
   0.5초에 한 건일 때는 잘 돌아가는 것처럼 보였다. **잘 돌아가 보이는 것이 가장 위험한 상태.**

8. **`accum` 의 주소를 그대로 넘기면 안 된다.**
   `PostMessage` 는 큐에 넣고 즉시 반환한다. UI 스레드가 꺼내 볼 때쯤이면 워커가 이미
   `memmove` 로 버퍼를 당겨서 그 자리에 다른 데이터가 있다. → 힙에 복사하고 소유권을 넘김.
   **`new` 는 워커 스레드에서, `delete` 는 UI 스레드에서** 일어난다.

9. **블로킹 `recv` 는 플래그로 못 깨운다.**
   `m_running = false` 로 바꿔봐야 `recv` 가 돌아와야 검사를 하는데 돌아오질 않는다.
   `closesocket()` 을 불러 `recv` 를 에러로 깨웠다. Java에서 `Thread.interrupt()` 대신
   `socket.close()` 를 쓰는 것과 같은 패턴.

10. **`winsock2.h` 는 `framework.h` 보다 먼저 와야 한다.**
    `windows.h` 가 `WIN32_LEAN_AND_MEAN` 이 없으면 옛 `winsock.h` 를 끌고 들어와 충돌한다.
    `pch.h` 최상단에 넣어 해결.

11. **`char` 와 `wchar_t` 는 다른 타입이다.**
    소켓은 1바이트 문자, MFC 유니코드 빌드는 2바이트 문자. `CString(const char*)` 로 변환했고,
    데이터가 순수 ASCII라 안전하다. 한글이 섞였다면 코드 페이지 문제가 생긴다.

12. **Windows의 `SO_REUSEADDR` 는 리눅스와 의미가 다르다.**
    리눅스는 `TIME_WAIT` 재사용만 허용하지만, **Windows는 살아 있는 서버가 있어도 bind 를 허용한다.**
    실제로 죽은 줄 알았던 예전 서버가 포트를 잡고 있어서 엉뚱한 서버에 붙는 사고를 겪었고,
    이 옵션을 제거해 `10048` 로 즉시 실패하도록 바꿨다.

13. **Windows에서는 블로킹 `accept()` 중에 `Ctrl+C` 가 안 먹는다.**
    Python 서버에서 겪었다. 리스닝 소켓에 `settimeout(1.0)` 을 걸어 주기적으로 제어권을
    회수하도록 해결. 6번, 9번과 같은 뿌리의 문제다.

14. **목록이 무한히 쌓인다.**
    장중 6시간이면 수만~수십만 건. `MAX_ROWS = 500` 으로 제한하고 오래된 행을 삭제.

## 9. 작성 범위 — 정직하게

면접에서 과장하지 않기 위해 구분해 둔다.

- **직접 작성:** 0단계 C++ 습작 전부, 콘솔 TCP 클라이언트, MFC 클라이언트 코드,
  현재의 Python 더미 서버.
- **AI 보조:** 학습을 도운 튜터 세션이 있었다. 규칙상 **완성된 코드를 통째로 받지 않고**
  몇 줄짜리 예시와 지시를 받아 직접 타이핑하는 방식으로 진행했다.
  다만 일부 오류 처리 블록과 서버 리팩터링은 안내받은 코드를 붙여넣었다.
- **폐기한 것:** 프로젝트 초반에 AI가 생성해 준 완성형 더미 서버(`tick_server.py`)가 있었으나,
  내용을 설명할 수 없다고 판단해 **폐기하고 처음부터 다시 만들었다.**
  (그 과정에서 AI가 만든 쪽이 Windows에서 `ConnectionAbortedError` 를 잡지 않아
  클라이언트가 끊기면 죽는다는 것도 실측으로 확인했다.)
- **작성 예정:** `server/PROTOCOL.md` 는 아직 AI가 쓴 초안이며, 본인 말로 다시 쓰는 중.

**설계 판단 중 튜터가 제안한 것** (이유는 이해하고 있으나 본인이 착안한 것은 아니다):

- `--split` 의 절단 위치를 `2` 로 잡은 것 — 길이 프리픽스조차 덜 온 상황을 만들기 위해
- 길이 프리픽스 방식 자체를 채택한 것 — 구분자 방식보다 학습 가치가 크다는 판단
- 워커 스레드 + `PostMessage` 구조
- 목록 최대 건수 제한과 `MAX_ROWS` 라는 접근

이 항목들은 **"왜 그렇게 했는지 설명할 수 있는가"** 로 물어야 하고,
"어떻게 그 아이디어를 떠올렸는가" 로 물으면 정확한 답이 나오지 않는다.

## 10. 물어볼 만한 질문

**프로토콜/네트워크**
- TCP에서 메시지 경계는 어떻게 잡았나? 왜 그 방식인가?

- 길이를 왜 big-endian으로 보내나? 안 그러면 무슨 일이 생기나?
- 받는 쪽 파서가 반드시 처리해야 하는 경우는 몇 가지인가?
- `--burst` / `--split` 테스트 모드는 각각 어떤 실수를 잡아내나?

**스레드/UI**
- 왜 소켓 수신을 별도 스레드로 뺐나? 안 빼면 어떻게 되나?
- 워커 스레드에서 UI 컨트롤을 직접 만지면 왜 안 되나?

- 데이터를 왜 힙에 복사해서 넘겼나? 버퍼 주소를 그냥 넘기면?

- 블로킹 중인 `recv` 를 어떻게 중단시켰나? 왜 플래그로는 안 되나?

**C++ / 메모리**
- 스택 객체와 힙 객체의 소멸 시점 차이는?

- 함수 매개변수를 `const T&` 로 받는 이유는?
- `memcpy` 와 `memmove` 는 언제 갈리나?
- `char` 배열에서 4바이트 정수를 읽을 때 왜 `memcpy` 를 쓰나?
- 이 프로그램에서 메모리 누수가 날 수 있는 지점은 어디인가?

**설계 판단**
- 목록 건수를 제한한 이유는? 값은 어떻게 정했나?
