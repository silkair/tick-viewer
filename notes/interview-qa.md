## 공통 원칙 세 가지

이걸 어기면 답변 내용이 맞아도 약해 보인다.

1. **문제 → 해결 순서로 말한다.**
   해결만 말하면 "어디서 보고 따라 했나" 로 들린다. 무엇이 문제였는지를 먼저 말해야
   이해했다는 게 전달된다.

2. **구체적인 숫자와 실제 출력을 쓴다.**
   `87바이트`, `[받음 2]`, `|9172758` — 직접 돌려본 사람만 가진 것이다.
   이게 없으면 책에서 읽은 얘기와 구별되지 않는다.

3. **'주문' 과 '체결' 을 절대 섞지 않는다.**
   주문은 "사겠다/팔겠다" 하고 내는 것이고, 체결은 그게 맞아서 **실제로 거래가 성사된 것**이다.
   내 프로그램이 받는 건 **체결**이고, 주문 계통은 만들지도 않았다.
   증권사 면접에서 이 둘을 섞으면 도메인을 모른다고 판단한다. 값싸게 잃는 점수다.

4. **답하기 전에 "지금 묻는 게 뭐지?" 를 속으로 되뇐다.**
   반복해서 나온 실수다. 질문에 답하지 않고 **아는 것을 말하는** 경향이 있다.
   - Q3 1차: "길이 프리픽스를 처음부터?" → 프로젝트 전체 개발 프로세스로 답함
   - Q11 1차: "**왜** PostMessage?" → "PostMessage로 넘겼습니다" (무엇만 답함)
   - Q12 2차: "주소를 그냥 넘기면 왜 안 되나?" → `memmove` vs `memcpy` 차이만 설명

   **첫 문장이 질문에 대한 직접적인 답인지 확인한다.** 배경 설명은 그다음이다.

5. **물어본 것에만 답한다.**
   특히 AI 활용은 **물어보면** 정직하게 답하고, 먼저 꺼내지 않는다.
   묻지 않았는데 첫 문장에 놓으면 "이 프로젝트 AI가 만든 건가" 라는 의심 위에서
   나머지를 듣게 된다.

## Q1. 만들어 보셨다는 프로그램, 어떤 건지 설명해 주시겠어요?

*(60초. 면접관은 C++는 알지만 이 프로젝트는 처음 듣는다)*

### 모범 답안

> TCP 소켓으로 주식 체결 데이터를 실시간으로 받아서, 창의 목록에 **한 줄씩 쌓아** 보여주는
> Windows 데스크톱 프로그램입니다. 증권사 HTS의 '시간대별 체결' 화면을 아주 작게 흉내 낸 겁니다.
>
> 만든 이유는, 제 실무 경력이 Java와 Spring이라 **C++이나 소켓, 데스크톱 GUI를 다뤄본 적이
> 없었기** 때문입니다. 책으로 읽는 것보다 작더라도 끝까지 동작하는 걸 하나 만들어보는 편이
> 낫겠다고 판단했습니다.
>
> 구성은 두 부분입니다. 데이터를 흘려보내는 **더미 서버를 Python으로** 만들었고,
> 그걸 받는 **클라이언트를 C++과 MFC로** 만들었습니다. 클라이언트는 소켓에서 받는 일을
> **별도 스레드**에서 하고, 화면 갱신은 UI 스레드로 넘겨서 처리합니다.
>
> 범위는 **시세를 받아서 보여주는 데까지**고, 주문이나 계좌 쪽은 없습니다.

### 왜 이 구조인가

- **무엇 → 왜 → 어떻게 → 범위** 네 덩어리다.
- 마지막 "범위" 문장이 중요하다. **먼저 선을 그으면** 면접관이 주문·체결 처리까지
  물어보다가 서로 헛도는 일이 없다.
- "한 줄로 띄운다" 가 아니라 **"한 줄씩 쌓인다"** 라고 말할 것. 실시간 누적이
  이 프로그램의 성격이다.

### 1차 연습 기록

> "TCP 소켓으로 주식 체결 데이터를 받아서 창에 한 줄로 띄워주는 프로그램. HTS의 시간대별 체결
> 화면을 흉내내었다. C++과 MFC를 사용했고 더미 서버를 파이썬으로 만들어서 구현했습니다."

**피드백**
- 사실은 전부 맞다. 첫 문장에 핵심이 있고, HTS라는 비유 대상을 댄 것도 좋다.
- 다만 **분량이 20초**다. 60초를 받았으면 왜 만들었는지와 범위까지 들어가야 한다.
- **왜 만들었나가 빠지면** 면접관이 질문 난이도를 못 정한다.
- 말끝이 "~했다" 와 "~합니다" 로 섞였다. 하나로 통일할 것.

## Q2. TCP로 데이터를 받는다고 하셨는데, 한 건이 어디서 끝나는지는 어떻게 아셨나요?

### 모범 답안

> TCP는 바이트가 순서대로 흐르는 **스트림**이라 메시지 경계라는 개념이 없습니다.
> 서버가 `sendall` 을 세 번 불러도 클라이언트의 `recv` 가 세 번 불린다는 보장이 없어서,
> **여러 건이 뭉쳐 오기도 하고 한 건이 반쪽만 오기도** 합니다.
>
> 그래서 본문 앞에 길이를 붙였습니다. **본문의 바이트 수를 4바이트 부호 없는 정수,
> 네트워크 바이트 순서인 빅엔디안**으로요.
>
> 받는 쪽은 이렇게 동작합니다. `recv` 로 받은 걸 일단 **누적 버퍼에 쌓습니다.**
> 4바이트 이상 쌓였으면 앞 4바이트를 읽어 길이 N을 구하고, **4+N 바이트 이상** 쌓였으면
> 한 건이 완성된 거라 꺼내서 처리하고 버퍼를 앞으로 당깁니다. 모자라면 **아무것도 하지 않고**
> 다음 `recv` 를 기다립니다.
>
> 이걸 `if` 가 아니라 **`while` 로 도는 게 중요한데**, 한 번의 `recv` 에 여러 건이
> 들어 있을 수 있어서입니다.
>
> 그리고 길이 값은 외부에서 온 값이라 그대로 믿으면 안 됩니다. 0이거나 버퍼 크기보다 크면
> 프로토콜 위반으로 처리하고 연결을 끊습니다.

### 왜 이 구조인가

- 이 질문의 진짜 의도는 **"TCP가 스트림이라는 걸 아는가"** 다.
  그래서 첫 문장이 반드시 **문제 진술**이어야 한다.
- 질문이 "어떻게 **아셨나요**" 이므로 **받는 쪽 알고리즘**이 답의 본체다.
  길이를 붙였다는 건 보내는 쪽 얘기일 뿐이다.
- 마지막 문단(길이 검증)은 **가산점**이다. 여기까지 말하는 지원자는 드물다.

### 헷갈리기 쉬운 것 — 물어보면 답할 수 있어야 한다

본문이 `152233|A0169000|1099.70|3` (25바이트)일 때 한 건의 실제 모양:

```
번호   0    1    2    3  │  4    5    6   ...   28
값    00   00   00   19  │  '1'  '5'  '2'  ...  '3'
     └──── 길이 4개 ────┘ └──── 본문 25개 ────┘

한 건 전체 = 4 + 25 = 29바이트
```

- **`4 + N` 은 위치가 아니라 개수다.** "29번 자리까지" 가 아니라 "총 29개".
- **`00 00 00 19` 는 16진수 표기**다. 문자 여섯 개가 아니라 **바이트 네 개**이고,
  값은 0, 0, 0, 25 다. 문자 `'0'` 의 실제 값은 48이라 전혀 다르다.
- 4바이트는 세어서 아는 게 아니라 **약속**이다. 맨 앞에서부터 무조건 4개.

| 쌓인 개수 | 상태 | 할 일 |
| --- | --- | --- |
| 0 ~ 3 | 길이도 못 읽음 | 아무것도 안 하고 대기 |
| 4 ~ 28 | 길이는 읽음. 본문이 덜 옴 | 아무것도 안 하고 대기 |
| 29 이상 | 한 건 완성 | 꺼내고 29개를 버림 |

### 1차 연습 기록

> "한 건이 어디서 끝나는지는 앞에 총 바이트 길이를 표시하도록 하여 구분했다."

**피드백**
- 답은 맞았는데 **한 문장이라 이해했다는 증거가 없다.** 들은 대로 했다는 인상을 준다.
- **문제 진술이 없다.** "TCP에는 메시지 경계가 없다" 가 반드시 들어가야 한다.
- **받는 쪽 알고리즘이 없다.** 질문이 요구한 건 그쪽이다.
- "총 바이트 길이" 보다 **"본문의 바이트 수를 4바이트 부호 없는 정수, 빅엔디안으로"** 가
  훨씬 낫다. 외우면 되는 것이고 값이 싸다.

## Q3. 그건 처음부터 그렇게 만드신 건가요?

*(Q2 직후에 나온 질문. "그건" = 길이 프리픽스다)*

### 이 질문의 의도

> **"직접 겪고 붙인 건가, 어디서 보고 따라 한 건가?"**

프로젝트 전체의 개발 프로세스를 묻는 게 아니다. **길이 프리픽스 하나**를 묻는 것이다.

### 모범 답안

> **아니요, 처음엔 길이 없이 그냥 문자열만 보냈습니다.**
>
> 그랬더니 받는 쪽 출력이 이렇게 나왔습니다.
> `172758|A0169000|1101.25|9172758|A0169000|1100.04|5`
> 앞 건의 수량 `9` 와 다음 건의 시각 `172758` 이 그대로 붙어버려서,
> **수량이 9인지 9172758인지 사람이 봐도 알 수가 없었습니다.**
>
> 그때 TCP에 메시지 경계가 없다는 걸 실감하고 길이 프리픽스를 붙였습니다.
>
> 그런데 붙이고 나서도 문제가 있었습니다. 로컬에서 테스트하면 한 번에 한 건씩 깔끔하게 와서,
> **파서가 맞는지 확인이 안 되더라고요.** 그래서 서버에 모드를 두 개 넣었습니다.
> **3건을 한 번의 `sendall` 로 붙여 보내는 모드**와, **한 건을 2바이트에서 잘라
> 나눠 보내는 모드**입니다.
>
> 2바이트에서 자르는 이유는, 그래야 **길이 4바이트조차 덜 온 상태**가 만들어지기 때문입니다.
> 절반에서 자르면 길이는 온전히 도착해서 더 쉬운 경우만 시험하게 됩니다.

### 주의 — 출처를 밝힐 것

`--split` 의 절단 위치를 `2` 로 잡은 것은 **튜터의 제안**을 받아들인 것이다.
물어보면 *"그 값은 조언을 받았고, 왜 그래야 하는지는 이렇습니다"* 라고 답한다.
이유를 설명할 수 있다는 것과 그 아이디어를 착안했다는 것은 다른 주장이다.

### 1차 연습 기록

> "우선 ai를 활용해서 코드를 확인하고 다른 파일에 처음부터 만들고 수정하는 과정을 거쳤다.
> 처음엔 값을 임의로 입력했고, 이후엔 서버에서 랜덤으로 생성하여 띄웠고 (…) 이후 ai의 코드와
> 비교하여 검증하는 과정을 거쳤다."

**피드백**
- **질문을 놓쳤다.** 길이 프리픽스를 물었는데 프로젝트 전체의 개발 프로세스로 답했다.
- **AI를 첫 문장에 놓은 것이 불리하다.** 묻지 않았는데 먼저 꺼내면
  "이 프로젝트 AI가 만든 건가" 라는 의심이 심기고, 그 위에서 나머지를 듣게 된다.
- **최고의 무기를 안 썼다.** `|9172758` 화면은 직접 겪은 사람만 가진 증거다.
  이걸 말하면 "따라 한 게 아니라 겪었구나" 가 한 방에 증명된다.

### 2차 연습 기록 — 크게 개선됨

> "처음에는 체결 데이터를 쭉 보내게 했습니다. 하지만 TCP 소켓 통신은 스트림이라서 메시지
> 경계가 없었고 그렇기 때문에 데이터가 이어져 있으면 어디가 한 건의 체결 데이터인지 구분할 수
> 없었습니다. 그래서 길이를 앞에 붙이는 방식을 적용했습니다."

**피드백**
- **시도 → 문제 → 원인 → 해결** 구조가 정확히 잡혔다. 질문 의도도 제대로 받았다.
- 남은 하나는 **실제 화면**이다. "구분할 수 없었습니다" 는 주장이고,
  `172758|A0169000|1101.25|9172758|...` 출력은 증거다. 한 문장 차이로 무게가 달라진다.

## Q4. 받는 쪽에서는 그 길이를 가지고 어떻게 처리하셨나요?

### 모범 답안

> 받는 쪽에 **누적 버퍼**를 하나 두고, `recv` 로 받은 건 무조건 거기에 이어 붙입니다.
> 그다음 두 단계로 검사합니다.
>
> **첫째,** 쌓인 게 4바이트가 안 되면 **길이 자체를 못 읽으니** 아무것도 하지 않고
> 다음 `recv` 를 기다립니다.
>
> **둘째,** 4바이트가 있으면 앞 4바이트를 읽어 본문 길이 N을 구합니다. 그리고 쌓인 양이
> **4+N 이상인지** 봅니다. 모자라면 본문이 덜 온 거라 역시 기다립니다.
>
> 4+N 이상이면 한 건이 완성된 거라 본문을 꺼내서 처리하고, **쓴 만큼인 4+N 바이트를
> 앞에서 잘라내고 뒤에 남은 걸 앞으로 당깁니다.** 그러면 다음 건의 길이가 맨 앞에 오게 됩니다.
>
> 그리고 이걸 **`while` 로 돕니다.** `recv` 한 번에 여러 건이 들어 있을 수 있어서
> 더 꺼낼 게 없을 때까지 반복해야 합니다. `if` 로 한 번만 하면 나머지가 계속 밀리는데,
> 실제로 3건씩 들어오는 모드로 테스트했을 때 **화면에 뜨는 시각이 실제 시간보다 점점
> 뒤처지는 걸** 확인했습니다.

### 절대 틀리면 안 되는 것

**`25` 는 고정된 기준값이 아니다.** 두 가지를 구분해서 말해야 한다.

| | 무엇 |
| --- | --- |
| **길이 (N)** | 앞 4바이트를 **읽어서 알아낸** 그 메시지의 본문 크기. 25일 수도 26일 수도 있다 |
| **쌓인 양** | 지금 버퍼에 들어 있는 총 바이트 수 |

비교는 `쌓인 양 < 4 + N` 이다. `25` 는 **데이터가 알려준 값**이지 내가 정한 상수가 아니다.
"길이가 25 이하라면" 이라고 말하면 *"25는 어디서 나온 숫자죠?"* 를 맞고 막힌다.

### 1차 연습 기록

> "받은 쪽에서는 그 길이를 확인해서 한 건의 체결 데이터가 온전하게 왔는지 확인합니다.
> 만약 길이가 25 이하라면 아직 모든 체결 데이터가 오지 않았다고 판단하여 다음 데이터까지
> 받아서 확인합니다. 그리고 확인된 체결 데이터는 지워서 다음 체결 데이터를 다시 앞에서부터
> 판단하게 합니다."

**피드백**
- **마지막 문장은 정확하다.** 버퍼를 당기는 동작을 말로 제대로 설명했다. 여기가 제일
  헷갈리는 대목인데 잡고 있다.
- **`25` 를 기준값처럼 말한 것이 사실 오류다.** 위 표대로 바로잡을 것.
- **관문이 하나만 나왔다.** "본문이 덜 왔나" 앞에 "길이 4바이트조차 안 왔나" 가 있다.
- **`while` 이 빠졌다. 이게 제일 크다.** 이걸 말하지 않으면 여러 건이 뭉쳐 오는 상황을
  겪어보지 않은 사람처럼 들린다.

### 2차 연습 기록 — 크게 개선됨

> "받는 쪽에서 누적되는 바이트를 계산하면서 새로운 값이 올 때마다 누적시킵니다. 누적된 게
> 4바이트가 안 되면 길이 자체를 읽을 수 없으니 다음 값을 기다립니다. (…) 처리한 만큼 앞에서
> 값을 잘라내고 모든 값들을 앞으로 땡깁니다. (…) burst로 한 번에 3건씩 값을 보냈을 때에는
> 3건이 왔는데 처리는 한 건이 되어 누적된 값이 계속 쌓이기만 하는 문제가 있었습니다.
> 그래서 while 문을 사용해 길이가 완성된 건은 모두 처리 되도록 하였습니다."

**피드백**
- **2단계 검사 · `while` 반복 · 당기기 · `--burst` 경험**이 전부 들어갔다. `25` 오류도 사라졌다.
- **용어:** "한 **주문**이 완성" → **"한 체결"**. 공통 원칙 3번 참고.
- **정확도:** "4바이트가 **넘으면**" 이 아니라 **"4바이트 이상이면"**. 정확히 4개일 때도 읽을 수 있다.
- **숫자를 붙이면 더 세다.** "누적이 쌓이는 문제가 있었습니다" 대신:
  > 매 라운드 약 58바이트씩 쌓였고, 그 속도면 **35초 만에 4096바이트 버퍼가 찹니다.**
  > 그 전에 이미 **화면에 뜨는 시각이 실제 시간보다 뒤처지는 게** 보였습니다.

## Q5. 길이를 붙이는 것 말고 다른 방법도 있었을 텐데요. 왜 그 방식이었나요?

*("구분자를 쓸 수도 있지 않나" 를 돌려 묻는 것. 선택지를 알고 골랐는지를 본다)*

### 세 가지 방식

| 방식 | 어떻게 | 실제 사례 |
| --- | --- | --- |
| **구분자** | 끝에 특정 문자를 붙이고 받는 쪽이 그걸 찾는다 | HTTP/1.1 헤더(CRLF), SMTP |
| **길이 프리픽스** | 앞에 길이를 붙인다 | HTTP/2, gRPC, Kafka, WebSocket |
| **고정 길이** | 매 건이 항상 정확히 N바이트. 길이도 구분자도 불필요 | 국내 거래소 전문에 흔함 |

### 모범 답안

> 크게 세 가지가 있습니다. **구분자**를 쓰는 방식, **길이를 앞에 붙이는** 방식,
> 그리고 매 건을 **고정 길이**로 맞추는 방식입니다.
>
> 구분자 방식은 사람이 읽기 쉽고 telnet으로 디버깅할 수 있다는 장점이 있습니다. 다만
> **본문 안에 구분자와 같은 문자가 들어가면 깨져서** 이스케이프 규칙을 따로 만들어야 합니다.
> 나중에 한글이나 바이너리를 실을 생각이면 부담이 됩니다.
>
> 길이 프리픽스는 **본문에 어떤 바이트가 들어 있든 상관없다**는 게 가장 큽니다. N개만
> 세면 되니까요. 그리고 받는 쪽이 **얼마나 더 기다려야 하는지를 정확히 알 수** 있습니다.
> 구분자 방식은 매번 버퍼를 훑어서 구분자를 찾아야 하는데, 이쪽은 앞 4바이트만 읽으면 끝입니다.
>
> 제 경우엔 본문 형식이 나중에 바뀔 수 있다고 봤고, 무엇보다 **받는 쪽 버퍼 관리를 직접
> 해보는 게 이 프로젝트의 목적**이라 길이 프리픽스를 골랐습니다.
>
> 다만 한 가지는 짚고 싶은데, **어느 방식을 골라도 부분 수신 처리는 똑같이 필요합니다.**
> 구분자를 쓴다고 해서 "버퍼에 쌓아뒀다가 완성되면 꺼낸다" 는 뼈대를 피할 수 있는 건 아닙니다.
> 구분자가 아직 안 왔으면 기다려야 하는 건 마찬가지니까요.

### 왜 이 구조인가

- **한쪽만 편들지 않는다.** 구분자의 장점(가독성, 길이를 미리 몰라도 됨)을 먼저 인정하고
  나서 선택 이유를 말해야 "알고 골랐다" 로 들린다.
- HTTP/1.1이 **둘 다 쓰는 것**이 좋은 예다. 헤더는 사람이 읽어야 하니 CRLF 구분자,
  본문은 크기를 알아야 하니 `Content-Length`.
- **마지막 문단이 핵심이다.** "이 방식이 좋아요" 만 말하는 사람과
  "어느 쪽을 골라도 본질은 같다" 를 아는 사람은 다르게 들린다.

### 2차 연습 기록

> "구분자 방식으로 했을 경우 구분자로 정한 문자가 체결 값에 포함되어 전달될 경우 오류가
> 발생할 수 있기 때문입니다."

**피드백**
- **가장 중요한 이유를 정확히 골라냈다.** 내용은 맞다.
- 문제는 **분량**이다. "왜 그 방식을 고르셨나요" 에 한 문장으로 답하면
  *"그거 하나밖에 모르는구나"* 로 받는다. 최소 세 덩어리는 필요하다.
- 빠진 것 셋:
  1. **구분자의 장점을 먼저 인정하기** — 사람이 읽기 쉽고, telnet 디버깅이 되고,
     길이를 미리 몰라도 흘려보낼 수 있다. 한쪽만 편들면 비교해보고 고른 걸로 안 들린다.
  2. **길이 프리픽스의 두 번째 장점** — 받는 쪽이 *얼마나 더 기다려야 하는지* 정확히 안다.
     구분자는 매번 버퍼를 훑어 찾아야 한다.
  3. **마지막 한 방** — "어느 방식을 골라도 부분 수신 처리는 똑같이 필요하다."
     이 문장이 있고 없고가 갈린다.

## Q6. 그 길이 값을 그대로 믿어도 되나요?

*(가장 흔한 함정. "믿을 수 있다" 고 답하는 순간 끝난다)*

### 모범 답안

> 아니요, 믿으면 안 됩니다. 그 길이는 **제가 계산한 값이 아니라 네트워크로 받은 값**이기
> 때문입니다. 서버가 세서 보낸 건 맞지만, **받는 쪽 입장에서는 외부 입력**입니다.
>
> 틀린 값이 올 수 있는 경우는 여럿입니다. 서버 버그일 수도 있고, **바이트 순서 변환을
> 빠뜨리면 25가 4억이 넘는 값으로 읽힙니다.** 상대가 악의적일 수도 있고요.
>
> 문제는 그 값을 그대로 썼을 때인데, 저는 `4 + 길이` 로 한 건의 크기를 구합니다.
> 길이가 `unsigned int` 최대값에 가까우면 **4를 더하는 순간 넘쳐서 아주 작은 수가 됩니다.**
> 그러면 "다 왔다" 는 검사를 통과해버리고, 실제로는 42억 바이트를 읽으려 들어서
> **버퍼 바깥을 건드립니다.**
>
> 그래서 길이를 읽은 직후, **그 값을 쓰기 전에** 검사합니다. **0이거나 버퍼 크기보다 크면**
> 정상적인 값일 수 없으니 프로토콜 위반으로 보고 연결을 끊습니다.
>
> 원칙으로 말하면 **바깥에서 온 숫자로 메모리를 다루기 전에는 반드시 범위를 확인한다** 입니다.
> Java였다면 `ArrayIndexOutOfBoundsException` 이 대신 잡아줬을 자리인데,
> C++에서는 아무도 안 잡아주니 제가 막아야 합니다.

### 핵심 구분

> **내가 계산한 값 ≠ 내가 받은 값**

바이트를 센 건 **서버**다. 받는 쪽은 그 숫자를 **네트워크로 건네받았을 뿐**이고,
그 시점에서 그건 사용자가 입력창에 친 값과 다를 게 없다.

### 이미 코드에 있다

```cpp
if (bodyLen == 0 || bodyLen > sizeof(accum) - 4) {
    // 프로토콜 위반
}
```

직접 넣은 코드다. **만들어두고 왜 만들었는지를 기억하지 못하면 면접에서 못 쓴다.**

### 1차 연습 기록

> "길이값은 체결 내용의 바이트 자체를 세는 과정이기 때문에 **믿을 수 있다고 생각합니다.**
> 하지만 검증 과정을 한번 추가하는 것도 좋을 것 같습니다. 예를 들어 한 체결이 완성됐다고
> 판단하고 값을 잘라낼 때 잘라낸 값만 따로 모아서 한번 더 길이 계산을 진행할 수 있을 것 같습니다."

**피드백**
- **전제가 틀렸다.** 이 질문이 노린 대답이 정확히 "믿을 수 있다" 다.
  센 건 서버고, 받는 쪽에게 그건 외부 입력이다.
- "검증을 추가하면 좋겠다" 는 방향은 맞다. 다만 제안한 방법이 **순서가 반대**다.
  **이미 잘라낸 뒤에는 늦다** — 잘라내는 그 순간에 버퍼 바깥을 읽어버린다.
  검사는 길이를 읽은 **직후**, 그 값을 쓰기 **전에** 해야 한다.

## Q7. 길이를 왜 big-endian으로 보내나? 안 그러면 무슨 일이 생기나?

### 모범 답안

> 숫자를 여러 바이트에 나눠 담을 때, **어느 바이트부터 쓸지가 CPU마다 다릅니다.**
> 25를 4바이트에 담으면 big-endian은 `00 00 00 19`, little-endian은 `19 00 00 00` 입니다.
> 같은 숫자인데 순서만 반대죠.
>
> 우리가 쓰는 x86 계열은 little-endian인데, **네트워크로 정수를 보낼 때는 big-endian으로
> 통일하기로 약속**돼 있습니다. 그걸 **네트워크 바이트 순서**라고 부릅니다.
>
> 그래서 서버는 Python에서 `>I` 로 big-endian 4바이트를 만들어 보내고,
> 클라이언트는 **`ntohl`** 로 되돌려서 읽습니다.
>
> 안 지키면 — 서버는 big-endian으로 보냈는데 클라이언트가 그대로 읽으면
> **25가 419,430,400으로 해석됩니다.** 그러면 "본문이 4억 바이트 온다" 고 믿고 영원히
> 기다리게 되고, 버퍼가 차서 멈춥니다. 저는 길이 검증을 넣어놔서 프로토콜 위반으로
> 걸리긴 하지만요.
>
> 그리고 이게 위험한 이유가 하나 더 있습니다. **양쪽 다 x86이면 변환을 빼먹어도 우연히
> 동작합니다.** 같은 순서로 쓰고 읽으니까요. 개발할 때는 멀쩡하다가 **다른 아키텍처가 붙는
> 순간** 터집니다.

### 숫자 확인 — 물어보면 답할 수 있어야 한다

```
25 = 0x00000019

big-endian    :  00 00 00 19   ->  읽으면 25
little-endian :  19 00 00 00   ->  big-endian 규칙으로 읽으면 0x19000000

0x19000000 = 25 × 16^6 = 419,430,400
```

`ntohl` 을 빠뜨리면 **정확히 이 숫자**가 나온다. 실제로 보게 되는 값이라 외워둘 만하다.

### 함수 짝

| | 보낼 때 | 받을 때 |
| --- | --- | --- |
| 4바이트 (길이) | `htonl` | **`ntohl`** |
| 2바이트 (포트) | **`htons`** | `ntohs` |

**h**ost ↔ **n**etwork, **l**ong / **s**hort.
이 프로젝트에서 `htons(9000)` 과 `ntohl(netLen)` 을 둘 다 썼다.

### 가산점 1 — Java와의 대비

> Java에서는 이 고민이 없습니다. JVM이 `DataOutputStream.writeInt()` 에서
> **무조건 big-endian으로** 씁니다. "Write Once, Run Anywhere" 를 위해 CPU 차이를 숨긴 거고요.
> C++은 CPU에 그대로 노출되니까 제가 명시해야 합니다.

### 가산점 2 — 문서화 효과

> 사실 서버와 클라이언트가 둘 다 x86이면 양쪽 다 변환을 안 해도 동작합니다. 그런데도
> `ntohl` 을 쓰는 이유는, **그 코드를 보는 사람에게 "이 값은 네트워크에서 온 것" 이라고
> 알려주는 표시**가 되기 때문입니다. 없으면 나중에 읽는 사람이 그냥 지역 변수인 줄 압니다.

여기까지 말하면 **"관례라서 따랐다" 가 아니라 "왜 관례인지 안다"** 가 된다.

## Q8. 소켓에서 받는 부분을 왜 별도 스레드로 빼셨나요?

### 모범 답안 — 짧게 원리만

> `recv` 는 **데이터가 올 때까지 돌아오지 않는** 함수입니다. 그걸 화면을 담당하는 스레드에서
> 부르면 그 스레드가 붙잡혀서 창이 멈춥니다. 그래서 **받는 일은 워커 스레드**에서 하고,
> **화면 갱신만 UI 스레드**가 하도록 나눴습니다.

Q9가 이어서 나오므로 여기서는 길게 말하지 않는다. 증거는 Q9에서 푼다.

## Q9. 안 뺐으면 어떻게 되나요? 직접 보신 게 있나요?

### 모범 답안

> 안 뺐을 때를 실제로 만들어봤습니다. `OnInitDialog` 에서 바로 소켓을 열고 받게 했더니,
> **창이 10초 동안 나타나지 않다가 20줄이 이미 채워진 채로** 떴습니다.
>
> 원인은 Windows 창의 구조입니다. 창은 **메시지 루프**라는 반복문이 돌면서 마우스 클릭,
> 키 입력, 화면 다시 그리기를 처리하는데, **그 루프를 담당하는 스레드가 `recv` 에 붙잡혀
> 있으면 아무것도 못 합니다.**
>
> 10초로 끝난 건 제가 **20건만 받고 멈추도록 제한을 걸어서 관찰이 가능하게** 만든 거고,
> 실제처럼 계속 받게 하면 **창이 영영 안 뜹니다.**
>
> 그리고 창이 늦게 뜨는 것보다 나쁜 게 있는데, 뜬 뒤에도 **마우스가 안 먹고, 다른 창에
> 가렸다 돌아오면 하얗게 남고,** Windows가 **"응답 없음"** 이라고 표시합니다.
> 사용자는 프로그램이 죽은 줄 압니다.
>
> 스레드를 나눈 뒤엔 창이 즉시 뜨고, 데이터가 들어오는 중에도 **창을 마우스로 움직일 수
> 있는 걸** 확인했습니다.

### 가산점 — Java 경력과 연결

> 웹 백엔드만 하면 이걸 겪을 일이 없습니다. Spring에서는 **톰캣이 요청마다 스레드를
> 붙여주니까** 제 코드가 블로킹이어도 다른 요청은 다른 스레드에서 처리됩니다.
> **데스크톱 GUI에는 그 "알아서" 가 없어서** 스레드를 직접 나눠야 한다는 걸 이번에 알았습니다.

### 절대 섞지 말 것 — 두 개는 다른 문제다

| 문제 | 증상 | 해결책 |
| --- | --- | --- |
| **응답성** | 창이 안 뜨고 얼어붙음 | **스레드 분리** |
| **처리량** | 데이터가 밀려 화면이 과거를 보여줌 | **`while` 반복** |

Q8·Q9는 **응답성** 질문이다. "실시간성이 부족했다" 고 말하면 두 번째 문제와 섞여서 흐릿해진다.

### 1차 연습 기록

> "처음에는 별도로 빼서 구현하지 않았습니다. 그렇게 했더니 문제가 하나 발생했습니다.
> 데이터를 받아오는 시간(처음에는 10초) 동안 체결 목록 창이 뜨지 않고 대기해야 했습니다.
> 실시간성이 부족하면서 기다려야 하는 불편함도 있었습니다. 때문에 별도 스레드로 관리하여
> 창을 띄우고 거기에 값이 하나씩 추가되도록 했습니다."

**피드백**
- 시도 → 문제 순서가 잡혀 있고 `10초` 실측도 있다. 뼈대는 좋다.
- **원인이 없다.** "창이 안 떴다" 는 현상이고, *왜* 못 떴는지(블로킹 + 메시지 루프)가 빠졌다.
  이 두 문장이 없으면 "겪었는데 왜인지는 모른다" 로 들린다.
- **증상을 절반만 말했다.** 늦게 뜨는 것보다 **얼어붙는 것**(마우스 무반응, 흰 화면,
  "응답 없음")이 더 심각하다.
- **`10초` 의 출처를 말하면 강해진다.** 20건 제한을 걸어 관찰 가능하게 만든 것이다.
  그냥 겪은 것과 실험을 설계한 것은 다르게 들린다.
- "실시간성" 은 처리량 문제 쪽 용어다. 위 표 참고.

## Q10. 받은 데이터를 화면 목록에 넣을 때, 워커 스레드에서 바로 넣으면 안 되나요?

*(셋 중 가장 중요. "잘 돌아가는데 왜 고쳤나" 를 묻는 질문이다)*

### 모범 답안

> 안 됩니다. **Windows에서 컨트롤은 그것을 만든 스레드만 만질 수 있습니다.** 창이 특정
> 스레드의 메시지 큐에 묶여 있어서, 다른 스레드가 동시에 내부 상태를 건드리면 자료구조가
> 깨집니다.
>
> 그런데 **실제로 해보면 잘 돌아갑니다.** 저도 처음엔 워커 스레드에서 바로 목록에 넣었고
> 멀쩡했습니다. **0.5초에 한 건이라 충돌할 일이 없었기 때문**입니다.
>
> **그게 제일 위험한 상태라고 생각합니다.** 초당 수백 건이 들어오고 사용자가 동시에
> 스크롤하면 깨질 수 있는데, **타이밍이 맞아야 터지는 버그라 재현이 안 됩니다.**
> 개발 중에는 안 드러나다가 거래가 몰릴 때 터지고, 로그를 봐도 원인을 못 찾습니다.
>
> 그래서 **데이터를 UI 스레드에 메시지로 보내고, 화면은 UI 스레드에서만 건드리도록**
> 바꿨습니다. 겉보기 동작은 그대로지만, 데이터가 몰려도 안 깨지는 구조가 됐습니다.
>
> 이 규칙은 Windows만의 것이 아닙니다. Swing의 `invokeLater`, Android의 `runOnUiThread`,
> JavaFX의 `Platform.runLater` 가 전부 **같은 문제를 푸는 장치**입니다.

### 이 답변의 힘

**"잘 됐는데 고쳤다" 를 정면으로 말하는 것.** 대부분은 "안 되니까 고쳤다" 만 말할 수 있는데,
**동작하는 코드를 이유가 있어서 고쳤다**는 건 판단력을 보여준다.

### 정직하게 — 직접 깨뜨려 본 적은 없다

| 주장 | 근거 |
| --- | --- |
| "워커에서 직접 넣어도 잘 돌아갔다" | **직접 확인함.** 3-c 단계의 실제 관찰 |
| "몰리면 깨진다" | **규칙에 근거한 것.** 겪은 게 아니다 |

*"직접 깨뜨려 보셨나요?"* 를 받으면:

> 아니요. 규칙을 알고 있어서 **터지기 전에 미리 고쳤습니다.** 이런 문제는 재현이 어려워서,
> 터진 뒤에 잡는 것보다 규칙을 지키는 편이 낫다고 판단했습니다.

**"겪었다" 고 말하면 안 된다.** 파고들면 바로 드러난다.

### 왜 0.5초에서는 안 터졌나 — 물어보면

`InsertItem` 이 목록의 내부 자료구조(항목 개수, 각 칸의 문자열, 스크롤·선택 상태)를 고치는
동안, UI 스레드도 화면을 그리려고 **같은 자료구조를 읽는다.**

```
워커:  항목 개수를 501로 늘림 → (아직 내용 안 채움) → 내용 채움
UI:                        이 순간에 501번째를 읽으면 → 깨지거나 죽음
```

`InsertItem` 이 걸리는 시간은 몇 밀리초다. **0.5초에 한 번**이면 그 짧은 구간에 UI 스레드가
하필 같은 것을 읽고 있을 확률이 거의 0이다. **위험한 구조라는 사실은 그대로고, 빈도가 낮아
안 드러났을 뿐이다.**

### MFC 쪽 사정 하나 더

MFC는 `HWND` 와 C++ 객체의 매핑을 **스레드별로** 관리한다. 그래서 다른 스레드에서
`m_tickList` 를 쓰면 그 매핑부터 어긋난다. 물어보면 덧붙일 수 있다.

### 2차 연습 기록 — 크게 개선됨

> "처음에는 목록에 직접 넣어 구현했습니다. (…) 워커 스레드가 아직 값을 채우기 전 ui 스레드가
> 그걸 읽어버리면 시스템이 깨지게 됩니다. 물론 제가 구성한 환경에서는 0.5초마다 데이터가
> 들어오기 때문에 실제 충돌은 일어나지 않았지만 데이터가 많아지면 충분히 발생할 수 있는
> 일이기 때문에 워커 스레드에서 목록에 직접 넣지 않도록 구현했습니다."

**피드백**
- **메커니즘을 정확히 설명했고, "실제 충돌은 일어나지 않았다" 까지 정직하게 말했다.** 원하던 답이다.
- **규칙 진술이 첫 문장에 없다.** "Windows에서 컨트롤은 그것을 만든 스레드만 만질 수 있습니다"
  를 먼저 말하고 그 뒤에 왜 그런 규칙인지를 붙여야 한다. 순서가 반대면 혼자 추론한 것처럼 들린다.
- **"동시에 같은 걸 읽는다" 가 아니라 한쪽은 쓴다.** 워커는 **쓰고**(`InsertItem` 이 내부
  자료구조를 고침), UI는 **읽는다**(화면 그리려고 훑음). 읽기끼리는 부딪히지 않는다.
- "시스템이 깨진다" 보다 **"목록이 깨져 보이거나 프로그램이 죽는다"** 가 구체적이다.

### 3차 연습 기록 — 하나 고치고 하나 잃음

> "새로운 값이 들어오는 타이밍과 ui 스레드가 값을 읽는 타이밍이 겹쳐 워커 스레드가 그 값을
> 수정하려고 하면 읽기와 쓰기가 겹쳐 오류가 발생할 수 있습니다."

**피드백**
- **읽기/쓰기 구분이 들어갔다.** 2차 피드백을 반영했다.
- **그런데 2차에 있던 "0.5초라 실제 충돌은 일어나지 않았다" 가 사라졌다.**
  그게 이 답변에서 제일 강한 문장이었다. 직접 겪은 것이고 "잘 되는데 왜 고쳤나" 에 답하는 부분이다.
  **고칠 때 있던 걸 잃지 않도록 조심할 것.**
- **규칙 진술이 두 번째로 빠졌다.** 맨 앞에 와야 한다.

**세 덩어리로 기억한다: 규칙 → 내 경험 → 해결.**

## Q11. PostMessage로 넘기셨다고 했는데, SendMessage도 있습니다. 왜 PostMessage였나요?

### 둘의 차이

| | 동작 |
| --- | --- |
| **`PostMessage`** | 큐에 넣고 **즉시 돌아옴**. 비동기 |
| `SendMessage` | 대상 스레드가 **처리를 끝낼 때까지 기다림**. 동기 |

### 모범 답안

> `SendMessage` 는 **대상 스레드가 처리를 끝낼 때까지 돌아오지 않습니다.** 동기 호출이죠.
>
> 워커 스레드에서 그걸 쓰면, **UI가 목록에 넣는 동안 워커가 멈춰 있게 됩니다.** 그동안
> `recv` 를 못 하니 데이터가 커널 버퍼에 쌓이고, 결국 수신이 밀립니다. **UI가 안 멈추게
> 하려고 스레드를 나눴는데 이번엔 워커가 UI에 묶이는 셈**이라 나눈 의미가 반감됩니다.
>
> 더 나쁜 경우로, UI 스레드가 다른 일로 막혀 있으면 **워커도 영원히 기다리게 되어 교착에
> 빠질 수 있습니다.**
>
> `PostMessage` 는 **큐에 넣고 즉시 돌아옵니다.** 워커는 바로 다음 `recv` 로 갈 수 있고,
> UI는 자기 속도로 큐를 비웁니다. **두 스레드가 서로를 기다리지 않는 게** 핵심입니다.

### 가산점 — 트레이드오프를 인정하기

> 다만 `PostMessage` 도 공짜는 아닙니다. UI가 느리면 **큐에 메시지가 계속 쌓입니다.**
> 지금은 초당 두 건이라 문제가 없지만, 초당 수천 건이라면 큐 길이를 보고 **오래된 건 버리는
> 처리**가 필요할 겁니다. 거기까지는 안 만들었습니다.

### 1차 연습 기록

> "데이터는 postMessage+힙복사로 넘겼습니다……"

**피드백** — 질문에 답하지 않았다. *무엇을 썼는지*가 아니라 *왜 그것을 골랐는지*를 물었다.
비교 대상(`SendMessage`)의 단점을 말해야 "골랐다" 가 된다.

### 2차 연습 기록 — F에서 크게 올라옴

> "sendMessage는 동기 처리됩니다. 때문에 워커가 ui에 묶이게 되고 목록에 값이 하나 들어가는
> 동안 워커가 멈춥니다. (…) 최악의 경우 교착 상태에 빠져 영원히 기다릴수도 있습니다. 때문에
> 바로 큐로 돌아오는 비동기 처리가 되는 postMessage를 사용했습니다."

**피드백**
- 동기/비동기, 워커가 묶임, 교착까지 다 나왔다. **질문에 제대로 답했다.**
- **말이 뒤집힌 곳:** "사용자는 실시간으로 데이터를 받을 수 **있습니다**" → **"없습니다"**.
  글이면 오타지만 말로 하면 뜻이 반대가 되어 면접관이 멈칫한다.
- **"바로 큐로 돌아오는" 은 부정확.** `PostMessage` 는 **큐에 넣고 호출한 쪽으로** 돌아온다.
- **메커니즘을 한 단계만 더.** "실시간으로 못 받는다" 앞에 →
  워커가 멈춘 동안 **`recv` 를 못 부르고**, 데이터가 **커널 버퍼에 쌓여** 수신이 밀린다.

## Q12. 워커가 파싱한 데이터를 UI 스레드에 넘길 때, 누적 버퍼의 주소를 그냥 넘기면 안 되나요?

*(이 프로젝트에서 가장 C++다운 질문)*

### 먼저 — `memmove` 가 무엇인가

**메모리 덩어리를 통째로 옮기는 함수.** Java의 `System.arraycopy` 와 같은 일을 한다.

```cpp
memmove(어디로, 어디서, 몇 바이트);
memmove(accum, accum + used, accumLen - used);
```

`--burst` 로 3건(87바이트)이 한 번에 왔을 때:

```
옮기기 전   [ 건A 29 ][ 건B 29 ][ 건C 29 ]      accumLen = 87
             ^accum    ^accum+29

건A 처리 완료(used = 29) → memmove(accum, accum + 29, 58)

옮긴 후     [ 건B 29 ][ 건C 29 ]                accumLen = 58
             ^accum
```

**처리한 앞부분을 버리고 남은 걸 앞으로 당기는 것.** 당기지 않으면 다음 바퀴에서도
여전히 건A의 길이를 읽는다.

**왜 `memcpy` 가 아닌가** — 원본(`accum+29 ~ accum+87`)과 대상(`accum ~ accum+58`)이
**겹치기** 때문이다. `memcpy` 는 겹치는 경우를 보장하지 않아 아직 안 읽은 부분을 덮어쓸 수 있다.
**"겹칠 가능성이 있으면 `memmove`"** 로 외운다.

### 왜 주소를 넘기면 안 되나

```
t=0   워커:  한 건 완성. accum+4 라는 "주소" 를 큐에 넣고 즉시 돌아옴
t=0+  워커:  memmove 로 당김 → accum+4 자리에 다음 건의 데이터가 들어옴
t=1   UI:   큐에서 꺼내 accum+4 를 읽음 → 엉뚱한 데이터
```

`PostMessage` 가 **즉시 돌아오기 때문에** 워커는 기다리지 않고 계속 버퍼를 헤집는다.

### 모범 답안

> 안 됩니다. `PostMessage` 는 **메시지를 큐에 넣고 즉시 돌아옵니다.** UI 스레드가 그걸
> 꺼내는 건 나중이고요.
>
> 그런데 워커는 기다리지 않고 계속 돕니다. 한 건을 꺼낸 뒤 **`memmove` 로 버퍼를 앞으로
> 당기거든요.** 그래서 UI가 꺼내 볼 때쯤이면 그 주소에는 **이미 다음 데이터가 들어와 있거나
> 지워져 있습니다.**
>
> 그래서 **힙에 복사본을 만들어 그 주소를 넘겼습니다.** 힙에 있는 건 `delete` 하기 전까지
> 사라지지 않으니 UI가 언제 꺼내 보든 안전합니다.
>
> 여기서 **소유권이 넘어갑니다.** 워커 스레드가 `new` 로 만들고, UI 스레드가 처리한 뒤
> `delete` 합니다. `new` 와 `delete` 가 다른 스레드에 있는 셈인데, 짝을 맞추는 건 여전히
> 제 책임입니다. **`delete` 를 빠뜨리면 체결 한 건마다 메모리가 샙니다.**
>
> Java였다면 이런 고민이 없습니다. 참조를 넘기면 **GC가 아직 쓰는 중인 걸 알아서 살려두니까요.**
> C++은 수명을 제가 관리해야 합니다.

### 비유

"저 칠판에 적어놨으니 이따 보세요" 라고 하면, 그 사람이 볼 때쯤 칠판은 이미 지워지고
다른 게 적혀 있다. **종이에 적어서 손에 쥐여줘야** 한다.

### 2차 연습 기록 — 질문에 답하지 않음

> "memmove는 값을 당길 때 사용합니다. copy를 사용할 수도 있지만 copy는 겹치는 값을 보장하지
> 않아 아직 안읽은 부분을 덮어버릴 가능성이 있어 memmove를 사용했습니다."

**피드백**
- **`memmove` 설명 자체는 정확하다.** 배운 것을 이해했다.
- **그런데 질문은 "주소를 그냥 넘기면 왜 안 되나" 였다.** `memcpy` 냐 `memmove` 냐를 물은 게 아니다.
- `memmove` 는 답의 **일부**다. 사슬을 끝까지 이어야 한다.

```
① PostMessage 는 큐에 넣고 즉시 돌아온다
② 그래서 워커는 기다리지 않고 계속 돈다
③ 워커는 memmove 로 버퍼를 앞으로 당긴다      <- 여기만 말했다
④ UI 가 나중에 그 주소를 읽으면 이미 다른 데이터
⑤ 그래서 힙에 복사본을 만들어 넘긴다
⑥ 워커가 new, UI 가 delete — 소유권이 넘어간다
```

**첫 문장은 이것이어야 한다:**
> **안 됩니다. `PostMessage` 가 큐에 넣고 즉시 돌아오기 때문입니다.**

그렇게 시작하면 `memmove` 얘기가 자연스럽게 붙는다.
**⑤⑥(힙 복사와 소유권 이전)이 이 답변의 결론이고, 이번엔 통째로 빠졌다.**

## Q13. 그렇게 힙에 만든 객체는 누가 해제하나요?

### 모범 답안

> **UI 스레드**가 합니다. 메시지 핸들러에서 데이터를 목록에 넣고 나면 그 객체는 더 쓸 데가
> 없으니, **마지막으로 쓰는 곳에서 지웁니다.**
>
> 안 하면 **체결 한 건마다 `std::string` 하나씩 샙니다.** 초당 두 건이면 하루 6시간에
> 4만 건 이상이고, 실제 시세 부하라면 훨씬 큽니다.
>
> 이 구조가 조심스러운 이유는 **`new` 와 `delete` 가 다른 함수, 다른 스레드에 있어서**
> 한눈에 짝이 맞는지 확인할 수가 없다는 점입니다. 보통 C++에서는 스마트 포인터로 이런 걸
> 줄이는데, **`PostMessage` 는 정수 하나(`WPARAM`)만 실어 나를 수 있어서** 날 포인터를
> 넘길 수밖에 없었습니다. 그래서 여기만 수동으로 짝을 맞췄습니다.

### 가산점 — 아직 안 막은 구멍 두 개 (정직하게 말하면 점수가 된다)

```cpp
std::string* pBody = (std::string*)wParam;
AddTickFromBytes(pBody->data(), (int)pBody->size());
delete pBody;      // 위에서 예외가 나면 여기 도달 못 함
```

> **① 예외 안전이 없습니다.** `AddTickFromBytes` 가 예외를 던지면 `delete` 를 건너뜁니다.
>
> **② 창이 닫힐 때 큐에 남은 메시지는 처리되지 않습니다.** 거기 실린 객체들은 아무도
> 지우지 않습니다. 프로세스가 곧 끝나니 실질적 피해는 없지만 구조적으로는 누수 경로입니다.

이 둘은 **"메모리 누수는 어디서 날 수 있나"** 질문의 답이기도 하다. 한 번에 두 질문을 처리한다.

### 1차 연습 기록

> "new는 워커 스레드에서, delete는 ui 스레드에서 한다."

**피드백** — 사실은 맞으나 한 줄이다. "누가" 만 답하고 **어디서 / 안 하면 어떻게 되나 /
왜 이 구조가 조심스러운가**가 빠졌다. 질문은 "이 구조가 위험하다는 걸 아는가" 를 본다.

## Q14. 블로킹 중인 recv 를 어떻게 중단시켰나요? 왜 플래그로는 안 되나요?

*(파싱과 무관한 **종료** 질문이다. 창의 X를 눌렀을 때 워커 스레드를 어떻게 끝내느냐)*

### 상황

창을 닫는 순간 워커 스레드는 여기 있다.

```cpp
while (true) {
    int n = recv(m_sock, ...);   // <- 데이터를 기다리며 자고 있음
}
```

창은 닫혔는데 워커는 `recv` 안에서 자고 있고, 프로그램이 안 끝난다.

### 왜 플래그로는 안 되나

```cpp
bool m_running = true;
while (m_running) { recv(...); }   // 종료 시 m_running = false
```

`m_running` 을 `false` 로 바꿔도, **`while` 조건을 검사하려면 `recv` 가 먼저 돌아와야 한다.**
데이터가 안 오면 영원히 안 돌아온다. **플래그를 볼 기회 자체가 없다.**

**비유** — 문 앞에서 택배를 기다리며 앉아 있는 사람에게 **벽에 "이제 그만 기다려" 라고 써
붙여도** 못 본다. 벨소리만 기다리고 있으니까. **문을 없애버려야** 일어난다.

### 모범 답안

> 창을 닫을 때 워커 스레드가 `recv` 안에서 **데이터를 기다리며 멈춰 있는 상태**입니다.
> 이걸 어떻게 끝내느냐가 문제였습니다.
>
> 처음 생각한 건 **불리언 플래그**였습니다. 종료할 때 `false` 로 바꾸고 루프 조건에서
> 검사하는 방식이요. **그런데 안 됩니다.** `while` 조건을 검사하려면 **`recv` 가 먼저
> 돌아와야 하는데**, 데이터가 안 오면 영원히 안 돌아옵니다. **플래그를 볼 기회 자체가 없습니다.**
>
> 그래서 **소켓을 닫는 방식**을 썼습니다. 창이 닫힐 때 `OnDestroy` 에서 `closesocket` 을
> 부르면, 그 소켓에서 기다리던 `recv` 가 **즉시 에러를 내며 돌아옵니다.** 이미 있던 에러 처리
> 분기를 타고 루프를 빠져나가면서 스레드가 정상 종료됩니다.
>
> 확인해보니 창을 닫는 즉시 서버 쪽에 연결 끊김이 찍히고, 작업 관리자에서도 프로세스가
> 바로 사라졌습니다.
>
> **Java에서도 같은 패턴입니다.** `Thread.interrupt()` 로는 소켓 읽기를 못 깨우고, 다른
> 스레드에서 `socket.close()` 를 불러 `SocketException` 을 터뜨리는 게 정석이죠.
> **"블로킹 I/O는 자원을 닫아서 깨운다"** 는 언어를 가리지 않는 패턴이라고 이해했습니다.

### 같은 문제를 세 번 만났다 — 묶어서 말하면 강하다

| 어디서 | 무엇에 갇혔나 | 어떻게 풀었나 |
| --- | --- | --- |
| Python 서버 | `accept()` | `settimeout(1.0)` — 주기적으로 깨어남 |
| MFC 창 | `recv()` (UI 스레드) | **스레드 분리** |
| 종료 처리 | `recv()` (워커 스레드) | **`closesocket()`** |

셋을 묶어 말하면 요령이 아니라 **블로킹의 성질을 이해했다**가 된다.
