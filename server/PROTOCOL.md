# 시세 전송 프로토콜

더미 서버(`tick_server.py`)와 C++ 클라이언트 사이의 약속.

## 1. 한 건의 생김새

```
[ 길이 4바이트 ][ 본문 ]
```

- **길이**: 본문의 바이트 수. **big-endian(네트워크 바이트 순서)** 부호 없는 4바이트 정수
  - Python: `struct.pack(">I", n)`
  - C++: `ntohl()` 로 되돌린다
- **본문**: ASCII 문자열. `시간|종목코드|가격|수량`

예시 — 본문이 25바이트일 때

```
00 00 00 19   31 35 32 32 33 33 7C 41 30 31 36 39 ...
└─ 길이 25 ─┘  └─ "152233|A0169000|1099.70|3" ─┘
```

접속: `127.0.0.1:9000`

---

## 2. 왜 길이를 앞에 붙이나

**TCP는 스트림이지 메시지 단위가 아니기 때문이다.**

Kafka나 HTTP를 쓸 때는 라이브러리가 "메시지 1개"를 잘라서 준다. TCP에는 그 개념이 없다. 서버가 `sendall()`을 세 번 호출해도 클라이언트의 `recv()`가 세 번 호출되리라는 보장이 전혀 없다.

`recv()` 한 번이 돌려주는 바이트 수는 **네트워크 사정, 커널 버퍼, 타이밍에 따라 매번 달라진다.** 실제로 이런 일이 일어난다.

| 상황 | recv() 가 돌려주는 것 |
|---|---|
| 운 좋을 때 | 정확히 한 건 |
| 서버가 빠르게 여러 건 보냈을 때 | **여러 건이 붙어서** 한 덩어리 |
| 패킷이 쪼개졌을 때 | **한 건의 절반** |
| 최악 | 1.5건 (한 건 + 다음 건의 앞부분) |

그래서 받는 쪽은 이렇게 해야 한다.

1. `recv()`로 받은 바이트를 **버퍼에 계속 쌓는다**
2. 버퍼가 **4바이트 이상**이면 앞 4바이트를 읽어 길이 `n`을 얻는다
3. 버퍼가 **`4 + n` 바이트 이상**이면 한 건이 다 온 것이다 → 잘라내서 처리
4. 잘라낸 만큼 버퍼에서 **제거**하고, 2번으로 돌아가 **반복** (한 번의 recv에 여러 건이 들어있을 수 있으므로)
5. 부족하면 아무것도 하지 않고 다음 `recv()`를 기다린다

**2~5를 `while` 루프로 돌리는 것이 핵심이다.** `if`로 한 번만 검사하면 붙어서 온 건들이 버퍼에 쌓인 채 밀린다.

> 실제 HTS 시세 수신에서 그대로 나오는 문제다. 초당 수백~수천 건이 들어올 때는 붙어서 오는 게 오히려 정상이다.

## 3. 파서를 괴롭히는 두 모드

파서가 맞는지 확인하려면 **일부러 최악의 입력을 만들어야 한다.** 그래서 서버에 모드를 넣었다.

```bash
py tick_server.py           # 기본 — 0.5초마다 한 건
py tick_server.py --burst   # 3건을 하나의 sendall 로 붙여서 전송
py tick_server.py --split   # 한 건을 두 조각으로 쪼개서 0.2초 간격 전송
```

- **`--burst`** → 4번(반복)을 빠뜨렸는지 잡아낸다. `if`로만 검사하면 3건 중 1건만 처리하고 나머지가 밀린다
- **`--split`** → 3번(길이 검사)을 빠뜨렸는지 잡아낸다. 반쪽짜리 메시지를 그대로 파싱하면 깨진 문자열이 나온다

**세 모드에서 모두 정상 동작해야 파서가 맞는 것이다.**

기본 모드만 통과하는 파서는 실제 시세 부하에서 반드시 깨진다. 개발 중에는 데이터가 드물게 와서 안 드러나고, 트래픽이 몰릴 때 터진다.

---

## 4. 메모리 관점

이 버퍼 관리가 C++ 학습의 핵심이다. Java에서는 신경 쓰지 않던 것들이 여기서 전부 나온다.

- 버퍼를 **어디에** 담나 — 스택인가 힙인가
- 잘라낸 뒤 남은 바이트를 **어떻게** 앞으로 당기나
- 버퍼를 **누가** 해제하나
- 목록에 계속 쌓이는 데이터의 **수명**은 누가 관리하나

여기서 세그폴트를 내보는 것이 목표다.
